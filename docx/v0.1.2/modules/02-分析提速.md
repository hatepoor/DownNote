## 背景

保存日记后心情记录要等很久才出来；有时其实已经分析完，界面却一直空着，要手动刷新才看到。三段耗时：

1. 心情分析与陪伴对话共用同一套生成参数（跟思考强度走，默认 low）；推理模型思考 token 计入输出预算，实测长度波动 170~1600+；
2. 生成链路最坏串行跑多次模型调用（非法 JSON 修正重试、空回复重发、危机复判叠加）；
3. 界面只在保存后 0 秒和 6 秒补拉两次列表，超过 6 秒才生成完的结果不自动刷出。

现状补充（实施对照）：`buildChatModel` 只处理"是否传入 `reasoning_effort`"（`cfg.reasoningEffort` 为空则完全不传），**没有显式关闭思考的分支**；条目状态目前只有 `analyzed` 布尔；分析写回**不校验正文是否已变**。

## 方案要点

### 1. 双档生成参数（chat / analysis）

- chat 档（陪伴对话）：继续跟随用户设置（温度、思考强度）不动。
- analysis 档（心情分析、危机复判共用）：模型三件套完全不变，仅生成参数不同——不开启思考、温度固定 0.8、`max_tokens` 800、不开惩罚参数（`top_p`/`presence_penalty`/`frequency_penalty` 均不传；顺带使"空回复去惩罚重发"在分析链路失去意义）。
- **"不开启思考"必须显式且可验证**（2026-10-08 已在目标端点实测，见下表），不能只靠"不传参数"：

  | 写法 | 思考内容 | 思考 token | 耗时 |
  |---|---|---|---|
  | **`reasoning_effort: "none"`（选定）** | 无 | 0 | 0.52s |
  | `reasoning_effort: "minimal"` | 有 79 字 | 43 | 0.54s |
  | `extra_body={"enable_thinking": false}` | 有 58 字 | 18 | 0.50s |
  | `extra_body={"thinking": {"type": "disabled"}}` | 无 | 0 | 0.35s |
  | 不传思考参数（改造前现状） | 有 67 字 | 21 | 0.66s |
  | 用户档 `low`（对照） | 有 61 字 | 35 | 0.65s |

  - 实测环境：`https://api.deepseek.com/v1` + `deepseek-v4-flash`，探针 prompt「计算 17 × 24，只输出数字」（2026-10-08）。
  - **选定 `reasoning_effort: "none"`**：与现有 `buildChatModel` 同一参数族，改动最小、跨 OpenAI 兼容网关通用；`thinking.type = disabled` 同样有效、留作备选（网关忽略 `none` 时可切）。
  - 反例一并留档：**不传参数、`minimal`、`enable_thinking: false` 都不能真正关闭思考**，不得当作"关思考"实现。
  - **温度另定 0.8**（2026-10-08，同一条 150 字日记 × 温度 0.3/0.6/0.8/1.0 各跑 3 次）：0.3 措辞重复僵硬（三次里两次逐字相同，"撑着"打转，用户反馈"太僵硬"）；0.8 措辞自然、标签与强度稳定（疲惫/委屈/希望、强度 5，不漂）、JSON 12/12 合法；提速不受温度影响（各档均 0.5~0.8s、思考 token 恒 0）。
  - 效果对照（真实端点、真实 `ANALYZE_MOOD_PROMPT`）：150 字日记在 chat 档 2.04s / 思考 251 token → analysis 档 0.78s / 思考 0 token；34 与 88 字的条目两档本就都在 1s 内（短条目模型自发不思考），收益集中在长而复杂的条目。

### 2. 时间预算（数值合同）

| 项 | chat 档（现状） | analysis 档 |
|---|---|---|
| 单次调用超时 | 60s | 30s |
| SDK 自动重试 | 5 次 | 2 次 |
| JSON 修正重试 | 2 次尝试 | 2 次尝试（沿用现有 `for _ in range(2)`） |
| 空回复重发 | 有（去惩罚重试一次） | 不叠加（惩罚参数本就关闭） |
| 生成链路总预算 | 无 | 90s，超出即落 `failed` |

- 前端轮询：间隔 2.5s、上限 120s（大于后端 90s 总预算，确保能观察到终态）；到上限停止轮询并保留手动刷新入口。
- 目标：正常网络下，保存日记到心情记录出现端到端 < 10s。

### 3. 条目分析状态机

`Entry.analyze_state` 取代 `analyzed` 成为唯一状态源（`analyzed` 保留一版作兼容镜像，写入时同步值；下个版本删除）：

| 状态 | 含义 | 进入 | 离开 |
|---|---|---|---|
| `pending` | 待分析（新建 / 编辑后 / 重启恢复 / 降级未开始） | 保存、编辑、启动恢复、结果被丢弃 | 认领成功 → `running` |
| `running` | 后台任务已认领、进行中 | 认领成功 | 成功 → `done`；失败 → `failed` |
| `failed` | 最终失败（重试与总预算耗尽 / 服务不可用） | 失败收口 | 手动刷新或兜底重试 → `running` |
| `done` | 已完成并落库 | 写回成功 | 编辑正文 → `pending` |

规则：

- **降级模式**：未配置模型时保存后保持 `pending`（不置 `failed`），界面按降级横幅语义呈现、不显示"分析失败"；配置完成后由兜底扫描自动处理。
- **中断恢复**：`running` 只代表"内存中的任务"；应用启动时执行 `UPDATE entries SET analyze_state='pending' WHERE analyze_state='running'`，随后由兜底扫描/进入应用触发重扫。
- **前端超时**：轮询到 120s 上限即停，不改变库中状态，保留手动刷新入口。
- 事件语义不变：分析成功才写心情记录，失败不写。

### 4. 迁移（旧库升级）

- `SCHEMA_VERSION` 6 → 7；新增 `_migrateToV7`：`ALTER TABLE entries ADD COLUMN analyze_state VARCHAR NOT NULL DEFAULT 'pending'`（新库 `create_all` 已带，旧库靠补列）。
- 回填：`analyzed=1 → 'done'`；`analyzed=0 → 'pending'`（旧库无法区分"曾失败 / 未开始"，统一 `pending` 交兜底重扫）。
- 消费方同步改造：
  - `listUnanalyzedIds` → 取 `analyze_state IN ('pending','failed')`（含重启遗留）；
  - `listDaysNeedingDiaryMemory`（日整合记忆沉淀）→ 判据由 `Entry.analyzed` 改为 `analyze_state = 'done'`；
  - `markEntryAnalyzed` → 写 `analyze_state='done'`（同步镜像 `analyzed=1`）；
  - `EntryRead` 增 `analyzeState` 字段，保留 `analyzed`（=`state=='done'`）一版兼容；`createEntry`/`updateEntry` 返回 `analyzeState='pending'`。
- 验收：含"已分析条目、未分析条目、整合日记"的 v6 旧库覆盖升级后——状态回填正确、旧心情记录不丢、兜底扫描能续跑。

### 5. 并发与旧结果丢弃

- **认领即互斥**：`UPDATE entries SET analyze_state='running' WHERE id=:id AND analyze_state IN ('pending','failed')`，`rowcount=1` 才执行分析；否则跳过（已有任务在跑）——手动刷新与兜底扫描不会重复分析同一条。
- **写回前校验正文未变**：认领时记下该条目的正文快照（内容与 `created_at`）；写回前重读，若已变化 → 丢弃结果、状态回 `pending`（交给针对最新正文的新任务），旧正文的心情记录绝不写回。
- 编辑路径保持"清旧心情 + 重新分析"，旧任务的写回被上一条校验拦下。
- 验收场景：① 手动刷新与兜底扫描同时命中一条 → 只发生一次写回；② 分析进行中编辑正文 → 旧任务结果被丢弃、最终心情对应新正文。

### 6. 界面（推送为主，轮询只作兜底）

- 分析状态由后端**推送**（SSE）：复用既有事件总线 `core/events.py` 的 `broker`，新增 `GET /api/entries/events`（与对话事件流同款，15 秒保活）；`analysis.py` 在 `done` / `failed` / 正文变动丢弃回 `pending` 三种终态各推一次，前端收到即刷新——**正常路径零轮询**。
- 兜底轮询只在推送通道不可用时启用（`EventSource.onerror` 即退回：5s 一次、上限 2 分钟）；另在提交/编辑后立即刷一次 + 5 秒补一次，兜住极端丢事件。
- 分析中：条目位置显示"分析中"（依 `analyzeState`）。
- 失败：显示「分析失败」+ 刷新按钮（**仅当 `failed` 且没有心情记录**——已有记录优先展示），点击调 `POST /api/entries/{id}/reanalyze` 回到分析中；30 分钟兜底扫描对 `failed` 条目自动重试，与手动按钮并存。
