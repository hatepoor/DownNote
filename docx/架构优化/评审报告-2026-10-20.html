Strong in-process

core/companion.py:30-32,124-155,192-196 · api/settings.py:23-24,114,138 · api/companion.py:29-36

api/settings.py

改键名改两处，编译期不报错，测试不会失败，实机才发现开关失效。

patrol(ignoreTiming=…, ignoreNextAt=…)

开发自测口子以布尔旗标编码进生产 interface，_skipReason 分支随旗标组合翻倍。

After · 键单一归属 + 具名豁免

core/companion.py 拥有 ENABLED_KEY

api/settings.py 只 import —— entryReply / persona 已经是这个风格，补齐即可。

patrol(now=…, skip={"timing"})

豁免规则是具名集合，不再是布尔真值表。

问题：同一文件里两种键归属风格并存，说明「键归谁所有」没有规则；旗标把理解成本转嫁给真值表脑内模拟。

方案：键常量收口到 core 模块；自测口子从布尔旗标改为显式具名参数。

  • 消除「实机才发现」类隐患
  • 同一 seam 一种用法，可推断
  • interface 参数从真值表变为白名单

与 ADR 无冲突。键收口是纯 dedup，可立即做；旗标重塑不必急。

4 · 会话生命周期散在三处，提示词快照缓存无 owner

Worth exploring in-process

agent/context.py:107-155 · api/chat.py:121,235-247 · core/companion.py:176

Before · 删除一个会话 = 人肉对齐三步

checkpointer.delete_thread
models.deleteSessionMessages / deleteChatSession
forgetPromptBlocks（忘记调 → 脏快照残留，注释自证）

正确性靠记忆维持：未来任何新的删除入口忘一步就埋雷。

After · 会话生命周期一个 interface

agent/session.py

createSession() / dropSession(sessionId)

checkpoint · 消息 · 快照失效，全部内收；缓存 dict 不再是模块级自由状态。

问题：缓存本身是必要复杂度（保 prefix cache），但四个自由函数 + 一个模块级 dict 摊开，删除语义散在三处靠人肉对齐。

方案：会话建/删/快照失效收成一处接口，端点只调一个函数。

  • locality：会话删除语义一处可见
  • 快照不变量有了封装 owner
  • 与候选 1 的回合 module 互相解套

与 ADR 无冲突；与 03-会话删除模块文档口径一致，方向是补强。

After · 注册与实现各归其位

scheduler.py = 纯注册表（浅得其所）

所有任务实现移入 core/，或 patrol 判定搬入——二选一，消除双重身份。

条目回应改事件订阅

analysis 只发「分析完成」事件，reply 生成订阅它，因果链显式化。

问题：理解「它为什么在此刻开口」要跳七站；scheduler 一半任务的实现住自己这、另一半住 core，归类标准不一致；「分析完成 → 可能有回应」的因果链藏在 analysis 函数体末尾。

方案：scheduler 变纯注册浅模块；条目回应触发从旁路调用改为事件订阅。

  • 每个任务的判定+实现集中一处
  • 因果链从函数体尾部移到事件
  • 不必合文件，只归位
注意：「纯程序判定、模型只说内容」是 05 模块文档的产品决策，重整时不得把判定挪进模型调用。
